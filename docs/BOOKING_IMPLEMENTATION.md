# Module 04 — бронирование площадок

Реализовано и проверено 11 ноября 2026 года. Учебная бронь DEMO в локальной H2;
она не резервирует зал в системе реальной площадки.

## Модель и жизненный цикл

`Booking` хранит площадку (FK), мероприятие (FK), сохранённую смету (FK),
ревизию и сумму сметы, валюту, владельца, название мероприятия, начало/конец
как UTC `Instant`, `timeZone=Asia/Almaty`, статус, время создания/отмены и
`@Version`. Индексы покрывают площадку/статус/интервал, владельца и мероприятие.

Статусы: `CONFIRMED → CANCELLED`. Отмена повторяема без изменения времени
первой отмены. Нельзя вернуть отменённую запись в CONFIRMED: новое подтверждение
создаёт новую запись. Nullable UNIQUE `active_event_id` дополнительно защищает
правило одной активной брони мероприятия; при отмене ключ освобождается.
DB CHECK проверяет положительный интервал и согласованность статуса/ключа.

При подтверждённой брони нельзя менять дату, площадку, гостей, бюджет, тип
мероприятия, пакет/смету или удалять мероприятие. Название, описание и способ
подбора менять можно. Проверки идут под тем же lock мероприятия. После отмены
редактирование/удаление разрешено; при удалении FK отменённых броней на event
и estimate обнуляются, неизменяемые исходные ID, ревизия, название и сумма
остаются в истории. Поэтому сохранённые snapshot ID после удаления могут
ссылаться на уже удалённые данные, а финансовые условия брони остаются читаемы.

Схема добавляется через существующий `ddl-auto=update`; рабочая база не
пересоздаётся. Фактический upgrade Module 03 → 04 проверен на отдельной
файловой H2. Для рабочей базы перед обновлением нужен штатный stop и backup.

## Время и смета

API требует ISO 8601 со смещением, например `2026-12-11T18:00:00+05:00`.
Любое явное смещение нормализуется в UTC; дата начала проверяется по
`Asia/Almaty` и должна совпадать с датой мероприятия. Начало в будущем,
конец строго позже начала, длительность не более 24 часов. Переход через
полночь разрешён. Точность не более микросекунды, чтобы H2 не округляла границы.

Подтверждение требует `estimateId` последней сохранённой ревизии, `CURRENT`,
неизменившиеся версии каталогов и `quoteComplete=true`. Preview не подходит.
Устаревшая/заменённая смета и неполная цена дают 409. Запись ссылается именно
на принятую сохранённую ревизию и копирует её сумму. Превышение бюджета остаётся
предупреждением; обязательного запрета для него в проекте нет.

## API

Все четыре endpoint требуют существующую сессию. Владелец берётся из неё;
чужие event/booking возвращают 404, отсутствие сессии — 401. Общий DEMO имеет
`ownerId=null`, историю общую для демо-профиля и расписание общее со всеми аккаунтами.

| Endpoint | Вход / результат |
|---|---|
| `GET /api/venues/{id}/availability?start=...&end=...` | 200: venueId, start/end UTC, timeZone, available; положительное смещение в URL кодировать как `%2B` |
| `POST /api/events/{id}/bookings` | JSON `{start,end,estimateId}`; 201: подтверждённая бронь |
| `GET /api/bookings` | 200: история текущего владельца, новые записи первыми, включая отменённые |
| `POST /api/bookings/{id}/cancel` | 200: отменённая бронь, слот освобождён |

Ошибки времени — 400. Конфликты — 409 с `message`, `errors`, `code`:
`VENUE_UNAVAILABLE`, `EVENT_ALREADY_BOOKED`, `ESTIMATE_OUTDATED`,
`ESTIMATE_INCOMPLETE`, `EVENT_BOOKED`. Контроллеры передают работу сервису;
конкурентная ошибка блокировки также преобразуется существующим advice в 409.

## Конкуренция и блокировки

Подтверждение работает в одной транзакции Spring с явно заданной изоляцией READ_COMMITTED:

1. Взять `PESSIMISTIC_WRITE` принадлежащего сессии мероприятия, проверить
   интервал и прочитать актуальную полную сохранённую смету под этим lock.
2. Взять `PESSIMISTIC_WRITE` строки выбранной Venue, даже если броней ещё нет.
3. Проверить одну активную бронь мероприятия и пересечение интервалов.
4. Вставить/flush Booking; освободить locks только после commit/rollback.

Общий lock строки Venue сериализует заявки разных мероприятий на один зал.
Проверяются только CONFIRMED, по условию:

```text
existing.start < requested.end AND requested.start < existing.end
```

Интервалы полуоткрытые: соседние `[16:00,18:00)` и `[18:00,22:00)` допустимы.
Отмена сначала получает маршрут ID без загрузки entity, затем locks event →
venue, перечитывает бронь и меняет статус в той же транзакции. Event edits,
удаление и сохранение пакета используют lock event. Обратного порядка locks нет.
GET availability служит подсказкой; POST всегда повторяет проверку под lock.
Прямые записи в БД вне сервисного протокола не поддерживаются.

## Интерфейс

«Мои мероприятия» → «Настроить пакет и смету»: открыть сохранённые пакет и
смету, указать начало/конец в Алматы, проверить доступность, подтвердить бронь,
увидеть статус и принятую ревизию/сумму, отменить и снова проверить свободный
слот. Вкладка также содержит историю всех броней аккаунта с явным обновлением.

Поля адаптируются под 390 px; используются существующие кнопки и стили.
Подтверждение доступно после положительной проверки и сохранения полной сметы.
Повторная отправка блокируется ref и disabled; изменение интервала инвалидирует
доступность. Ошибки сети видимы, 409 сбрасывает доступность. При потере ответа
подтверждения/отмены UI перечитывает историю, потому что транзакция могла
успеть завершиться. Сервер остаётся источником истины.

## Ограничения

Один зал Venue считается одним ресурсом. Нет расписания работы, буферов,
платежей, уведомлений, переноса, коммерческих сроков отмены или интеграции с
площадками. Бронирование не связывает длительность аренды с количеством часов
отдельных услуг в смете. Все цены и брони DEMO. Сессии после рестарта требуют
повторного входа. Приложение рассчитано на один процесс с файловой H2;
переезд на другую СУБД требует проверки lock/isolation и миграций схемы.
